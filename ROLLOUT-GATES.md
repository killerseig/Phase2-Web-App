# Minimum rollout gates: metadata and source analysis

Read-only production metadata: GRAPH_CLIENT_ID, GRAPH_TENANT_ID, GRAPH_CLIENT_SECRET and OUTLOOK_SENDER_EMAIL exist. FORM_TRANSLATION_API_KEY returns 404. formEmail and sdsWorkspace are ACTIVE. formEntries, scopedIntegrationApi and deliverFormEmail return 404; inventory has no alternate form delivery event worker. No secret payload or IAM setting was accessed/changed.

Ordinary dependency fix: report handlers now reuse only the existing Graph bindings. SDK manifest verifies no translation parameter/module is discovered. Functions compilation, 6 focused email/gallery tests, repeated-photo ownership/rendering and bilingual injected-adapter PDF tests passed. No actual transport occurred. Translation is deferred and no API key is required for the ordinary report email release.

New endpoints requiring separate approval:
- formEntries: propose allUsers Cloud Run invoker solely on formentries, so Firebase browser callables can reach it. Handler requires verified Firebase Auth, existing active user, current entry-reader policy and existing job access on every returned record. No secrets. Risks: a new internet-reachable submitted-data/export surface and authenticated request/export costs. No public data access or new employee reader roles are proposed.
- scopedIntegrationApi: optional independent rollout; propose allUsers solely on scopedintegrationapi, because its server-to-server client authenticates with application bearer rather than Cloud IAM. It checks hash, expiry/revocation, active Admin actor, explicit form/folder scopes, quotas and request replay. No secrets binding/provisioning endpoint. Possession of an approved bearer permits scoped writes; unknown-key traffic still costs bounded lookups. Endpoint deployment alone does not supply a usable credential. Existing approved credential may be used if its ownership/scopes are verified separately; do not create/share a key in this approval.
- deliverFormEmail: new Firestore create trigger on formDeliveries/{id}, using existing runtime service account 792793988588-compute@developer.gserviceaccount.com and existing four Graph bindings. No allUsers audience proposed: only its Eventarc delivery identity should invoke it. It will send real results to the recorded recipients of future queued submissions; submitted records remain immutable, send claims prevent blind repeats, uncertain sends need reconciliation. Deployment may require Eventarc APIs/receiver/invoker roles; exact missing API or IAM changes are not established and must be presented before granting them. Do not backfill old queued records automatically.

Optional, excluded from the pushed runtime exports/UI: publicFormRecipientVerification (public capability-bound callable with exact-address codes, Graph bindings and anti-abuse limits) and formTranslation (authenticated entry policy, Admin-only corrections, absent translation key and external content processing). Neither is necessary for a signed-in reporting rollout. Public respondent additions currently remain saved but excluded from mail without verified proofs; do not promise those recipients delivery.

Independent existing-function updates can be staged while preserving their current IAM/runtime identities: formTemplates, formWorkspace, formSubmissionViewer, sdsWorkspace and the now-decoupled formEmail. No new credential is required; prove before/after configuration and existing-client compatibility during deployment. sdsWorkspace supports the old load response by default, with metadataOnly opt-in plus new page/import operations. Updating formEmail alone supplies explicit retry behavior, not the absent automatic worker.

Do not deploy the entire broader Hosting bundle alone: Company Library/SDS requests the new page/import operations; entries calls the absent formEntries; private PDF/gallery enhancements need the updated viewer; automatic repeat-photo email needs the revised handler and approved worker. A separately built Reports-only or legacy-library surface could be released but would omit requested results and need a separate scoped build/test. API deployment is not a prerequisite for human Reports/Library use. No forms are published by a Hosting release.
